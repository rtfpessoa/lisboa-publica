Date: 2026-09-26. Status: plan and local implementation accepted after independent reviews, main-owned fixes and final requirement verification. Production remains unchanged.

The main agent owns planning, research, implementation, tests and corrections. Only the existing real `quasar-alpha` reviewers at `xhigh` perform independent reviews. Commit/push/deployment require the later execution instruction; prior security deployment authorization does not execute this proposal.

The [Wayfinder map](/Users/rodrigo.fernandes/docs/wayfinder/lisboa-provider-continuity-overlays/MAP.md) tracks the decisions. This document specifies the proposed changes and verification order. The user explicitly chose: “keep last-known information and positions for 1h, mark as inactive/not updated after 5 minutes of no data.” This settles the display policy: one-hour expiry and five-minute inactivity are separate from eligibility for current metrics. Both clocks use the original observation time; only a genuinely newer observation advances them.

## Problem and intended result

CP was reproduced going **16 → 12 → 0** in both TML and the application. Newest CP timestamps stopped advancing; public TML publisher code filters reports older than 90 seconds and requires matching rides. Our successful empty-snapshot replacement then removes markers and current counts. Errors already preserve previous rows, so treating all empty results as errors or increasing our 180-second age limit would not address the observed mechanism. Partner-side reasons remain unknown. [Accepted continuity evidence](research/PROVIDER-CONTINUITY.md).

Make temporary gaps understandable with explicitly last-known positions, original timestamps and strict expiry, without counting them as current operation. Then expose the three providers' official paths through the existing geometry API and map controls. Source/provider quotas, five-second refresh, public UI, Metro-only initial selection, existing 30-day/300-second history, 5 GB storage guard and security controls remain intact.

## Stage 1: truthful observation continuity

### Contract and stored state

Use the existing `LiveData` cache with two collections: `Vehicles` contains the latest successful normalized snapshot; an optional `LastKnown` slice contains omitted, bounded display candidates. Preserve existing gzip cache chunks and publication locks. No new database table, history stream, queue, collector service or cache framework.

The single `api/openapi.yaml` adds:

- `Vehicle.last_known`: required boolean. True means this response presents a previous position rather than a usable current source report; it never changes `position_kind`.
- `Vehicle.inactive_at`: required date-time, original `observed_at` plus five minutes. At or after this instant show “Inativo / sem atualização”, including a row still repeated by a healthy feed. This is a freshness label, not proof the physical vehicle stopped.
- `Vehicle.last_known_expires_at`: required nullable date-time. Implementation refinement: also include the deadline on current rows so a disconnected client can expire cached positions; the original `observed_at` plus one hour determines expiry. Set for every projected last-known row, including healthy-feed stale reports.
- `Operator.last_known_truncated`: required boolean. True when resource caps omit otherwise eligible previous positions; UI shows a clear bounded-display notice.
- `Operator.last_known_positions`: required nonnegative integer, computed for the capped, deduplicated projected display union, not just internally omitted rows. Existing nullable reported/estimated counts continue to mean usable current positions; unknown source availability yields null, while a valid empty snapshot yields zero.

- `Metrics.live_coverage`: required enum `complete | partial | unavailable`; `Metrics.unavailable_live_operators`: required array of selected operator IDs with unverified current coverage. These describe only the live reported/estimated totals, independently of historical metric availability.

Regenerate Go server/types with the existing v2 `oapi-codegen` setup and TypeScript with `oazapfts`; never edit generated files manually. No new API endpoint or scope is needed. New fields have safe zero/null values when decoding old caches; API projection explicitly sets them. Old executable versions ignore the optional internal `LastKnown` cache member on rollback.

### Successful refresh and omission

Within `PublishMu`, validate/normalize the source before changing state. Count and stage history using actual new source rows only. Inventory rows that are repeated, regress timestamps or fail the replay guard must not reach any history observation seam; keep explicit eligible-new-row selection independent of full `Vehicles` source inventory. For a successful snapshot, move previously observed but now omitted vehicles into `LastKnown`, merging only unexpired prior candidates and removing IDs actually present again. Explicit authoritative removals must discard both collections; the current JSON feeds expose no tombstone protocol, so do not invent one or infer trip completion from omission.

The approved display horizon is **one hour from original `observed_at`**, with inactivity at **five minutes from that same timestamp**, not from first omission, collection time, a repeated response or restart. Do not modify `observed_at` or the retained report's `collected_at`. Expire at the boundary, reject invalid/future observations using existing validation, deduplicate IDs and cap the projected last-known union at **500 per operator** (omitted, unverified-source and healthy-source stale rows combined). Apply the same cap to stored omitted candidates. On overflow keep newest observation times, with ID as deterministic tie-breaker; log bounded aggregate eviction counts without new high-cardinality logging. The cap bounds display memory, not provider inventory completeness. Keep a bounded `LastKnownTruncatedUntil` timestamp in the live cache, extended only to the maximum original expiry of evicted eligible candidates. Read-time projection additionally detects overflow in the full deduplicated union. The truncation flag is true while either condition applies, including after restart; it is not silently cleared by a refresh of an already-capped slice. UI states that only the most recent previous positions are shown. This conservative notice can persist until the original eviction horizon even if an ID recovers; no evicted-ID list is needed.

Apply the common snapshot behavior to all eight operators. Metro candidates retain `position_kind=estimated` and a distinct “Última estimativa” label. CM's documented array reports all vehicles' last known positions; this feature does not reclassify its present-but-old rows as active operation. Keep actual rows in `Vehicles` for source provenance and history decisions. One common read projection treats present rows older than 180 seconds as last-known, deduplicates them with omitted/unverified candidates, and applies the same cap and one-hour expiry. At five minutes they become inactive; at one hour their live-map positions/details expire even if the feed still repeats them. This does not delete the provider's static fleet inventory or existing historical records.

### Failures, freshness and API projection

On HTTP/JSON/source errors, keep the previous successfully published state and error status. Do not claim zero current operation or advance collection/observation timestamps. Present its eligible previous rows as last-known when the source is unverified (error, loading/restored without a new fetch, or collection older than the existing 90 seconds), apply the same one-hour original-time expiry and five-minute inactivity and expose current operator counts as null. A successful empty snapshot instead exposes zero current counts and may expose nonzero last-known count. Preserve source error/loading messages.

Rows from a healthy recent snapshot retain existing 180-second observation-age handling; old rows become projected last-known and are excluded from current metrics; they are listed only within the one-hour display horizon and cap. Omitted/failed-source last-known rows are always `stale=true`, including those younger than 180 seconds. Exclude them from current reported/estimated totals immediately. Clear sampled speed on last-known API rows to avoid showing a historical speed as current.

Use one shared projection for ListVehicles, ListOperators and live counts in GetMetrics, with a single captured clock per response. Only a successfully fetched source state (`ok` or observation-age `stale`, with no source error/loading/restored-unverified condition), collected within 90 seconds, contributes a known subtotal; valid empty coverage contributes zero. Include selected operators with no LiveData when identifying unknown coverage. Mixed known/unknown selections return the known reported/estimated subtotal with `live_coverage=partial` and the unavailable IDs; all unknown returns null totals with `unavailable`, all known returns totals (including zero) with `complete`. Apply route filtering to usable rows; do not infer coverage from an empty route result. The UI must label partial totals explicitly. Historical aggregates remain observation-based and their existing `unavailable_fields` are unaffected.

Compute expiry/counts at read time as well as refresh time so a failed/stopped collector cannot keep a position displayed forever. Expiry changes list membership, so preserve pagination deliberately: use a vehicle-specific revision wrapping the existing state revision and first-page `as_of` timestamp, following the existing schedule revision pattern. First-page eligibility is pinned for subsequent pages. Implement a narrow vehicle-revision lookup: a new `v:` token may resolve the current state even if its publication is older than five minutes; noncurrent states retain the existing five-minute age and version-eviction rules. Validate token `as_of` with `state.Created <= as_of <= now` and `now-as_of <= five minutes`; stale paging tokens return 410 and malformed/future timestamps return 400. First-page requests always capture now, even for a stopped collector whose current state is over five minutes old. Do not globally extend Cache.state or retain more versions. Implementation resource refinement: reduce the existing revision cap from 256 to 64; retain the maximum five-minute age and existing 410/reload handling. Under high publication churn, older pagination tokens may expire earlier. Archive display copies omit the collector replay ledger without mutating in-flight states; the current state and durable cache preserve it. Publication-only history Samples are also omitted from display revisions. Static replacements preserve the original frozen-page behavior within the bounded version cache. Stream large static arrays into the existing gzip JSON format instead of buffering an entire timetable/network during encoding; keep exact field, omission, nil-array and durable-cache compatibility. Legacy bare state revisions keep their existing five-minute lookup policy and publication-time eligibility; an aged current state is supported through the new token, not by changing legacy semantics. Do not create a second cache. Clearly document that pinned responses are a view at their `as_of`, and expired last-known rows must not be rendered even if a page was fetched before expiry. New unpinned reads must exclude expired candidates. Keep sort/filter/pagination order stable and protect `read:transit` scope, validation and rate limits.

Filter last-known candidates with the same operator and route filters; preserve verified plan provenance. Never reassign an old report to a new plan or fabricate a route link. Plan changes invalidate incompatible route links. Immutable cache values and their older revision memberships must not be mutated.

### Recovery, history and restart

Recover an ID using its actually reported observation; reject timestamp regression against both latest-source and retained candidates. Equal-timestamp reappearance can restore source membership but supplies no new history or movement sample and must not clear a discontinuity. A first genuinely newer report after omission/error starts a new movement baseline; speed/distance require the next valid consecutive report. Do not use a display candidate as a movement predecessor across the gap.

Keep minimal per-ID continuity metadata in the same live cache: highest accepted observation timestamp and a discontinuity bit. Mark discontinuous on omission, source failure/unverified freshness, restoration and eviction; derive elapsed source freshness and prior error status again under the publication lock on the next refresh, even when no collector ran during the gap. Readers never mutate the ledger or older cache versions; only a genuinely newer accepted report resets its baseline.

Preserve metadata independently of display-candidate expiry/eviction, without retaining coordinates or metadata copies. Implementation resource refinement: bound it to 2,000 IDs per operator (reduced from the proposed 10,000 after the worst-case resource probe), and a one-hour replay window; prune by original high-water timestamp, never by request/reappearance time. If capacity evicts entries, advance an operator-level replay floor to the maximum evicted high-water timestamp. For every ID, observations at/before that floor or at least one hour old may preserve source inventory but supply no new history/movement sample. Unknown IDs always start with a fresh baseline; if a prior baseline is at/before the floor, the first report above it also starts a fresh baseline. This conservatively suppresses potentially repeated history during extreme churn instead of silently losing the replay guarantee.

On restoration preserve saved high-water entries, mark all baselines discontinuous and advance the replay floor to at least restoration time plus the existing 30-second `providerClockSkew`, including legacy caches with no ledger. Apply this restart floor to every ID (including known IDs), so observations accepted after the last durable cache write cannot be replayed into compact history. Pre-restart reports may still be displayed by original age, but new history waits for an observation beyond that restart/skew floor; expose the existing history-collection status without fabricating a missing sample. Cache/ledger and eligible history writes share the existing transaction; no write-cadence increase. This bounded internal bookkeeping is part of LiveData, not a new store/service. Never clear anti-replay metadata just because a display position expires. Clock comparisons and eviction rules must be tested deterministically.

Keep `LastKnown` and continuity bookkeeping out of **every** history path; feed only the eligible new source observations (not the full repeated inventory) into `stageLive`, compact `prepareHistory`/collector proposals and raw history mode. Storing it in the live gzip cache is allowed; inserting it into snapshots is not. Errors may still flush already observed pending history under existing rules, but must not observe display candidates or manufacture samples. Database failures and storage pauses keep current live publication working through the existing guarded paths. Preserve the existing bounded partial-history policy: transaction/cache-write failure leaves compact pending proposals unacknowledged for normal bounded retry, while a successful cache commit whose guard denied history admission acknowledges and drops those closed records. Collection while paused supplies no new samples; expose the existing paused/unavailable status and do not backfill display candidates. In raw history mode, a failed write may lose those eligible samples after memory advances; retain the existing bounded partial-loss behavior with error logging/status, rather than introducing a retry queue or replaying reports as new history. Tests must demonstrate these limits explicitly.

On restore, discard expired/over-cap candidates, never rejuvenate timestamps, and treat restored source rows as unverified until a successful fetch. Old caches without `LastKnown` load normally. Retention, locks, write cadence and fail-closed storage reservations remain unchanged; no schema migration is required for the cache member.

### UI behavior

Keep all rows for display separately from usable current metrics. Use `last_known`, `stale`, expiry and source availability explicitly; do not derive currentness from age alone. The map dims last-known symbols; selected details show original time and “Última posição reportada” or “Última estimativa”. Before five minutes these are previous positions awaiting an update; at `inactive_at` additionally show “Inativo / sem atualização” and grey inactive styling. The same UI clock updates inactivity without a provider response. Selected vehicle information survives within the one-hour window; neither stage implies the vehicle is operating now. Exclude expired markers/details on the existing five-second UI clock and on response updates; backend expiry is exact and UI removal may lag by at most one existing refresh interval. Expired selected details show “Posição anterior expirada” rather than a current position.

Operator buttons remain selectable and keep `aria-pressed` when reports disappear. Show current report count separately from last-known count, valid empty coverage, source error and loading. Mixed selections must identify partial/unverified coverage rather than replacing unknown counts with zero. History/fleet views keep their existing period-based availability. Do not add a new settings screen, user-adjustable TTL or inferred train motion.

## Stage 2: official rail and ferry paths

[New archive research](research/RAIL-FERRY-PATHS.md) verifies current TML normalized plans: CP `76XA2`, TTSL `YYS70`, Fertagus `2XUL7`. The preliminary probe found referenced geometry for **44/44, 5/5 and 2/2** routes, with **77, 17 and 4** candidate variants. Actual new-mode validation rejects CP variants with conflicting coordinates at duplicate sequences: usable coverage is **36/44 routes, 57 variants, partial**. TTSL remains **5/5, 17 variants** and Fertagus **2/2, 4 variants**. Identical duplicate points are normalized; ambiguous variants are omitted whole and visibly labeled partial. Catalogue URL discovery and existing permitted-host/TLS/budget checks remain authoritative. No direct-feed fallback or new entitlement is necessary.

Enable geometry construction and the existing 2.5-million-point guard for train/ferry modes in `gtfs_parser.go`. Retain only variants referenced by trips with locally retained stops for these new modes; current fixtures already satisfy that rule. Preserve shape/direction/headsign/plan provenance, variant IDs, original vertex order and existing two-metre simplification. Keep complete locally referenced CP service paths, including their continuation outside Lisbon. Do not clip by dropping vertices, connect separate discarded segments, import every national route or label this as a full physical railway track inventory.

Make optional geometry failure independent of valid routes/stops/schedules. A missing/malformed shape table or individual variant, optional geometry point/variant overflow, or geometry cache-admission failure must leave already validated static services publishable. TLS/host policy, HTTP download bounds, ZIP integrity, expansion/entry/row limits and required base-GTFS validation remain fatal for the refresh; retain the previous static state and report error instead of publishing a corrupt or unsafe archive. Do not bypass any 64 MiB download, 512 MiB expanded, 256-entry or five-million-row archive guard to recover optional geometry. Use the existing `GeometryError`/timestamp/coverage mechanism. For these GTFS operators, retain prior geometry only when plan and current route/shape references are compatible, preserving its old timestamp and stale label; on a new plan with invalid geometry expose unavailable paths. Strip both shape arrays and attached route geometry when admission fails, then recheck the base static cache. Never weaken the 128 MiB write allowance or 5 GB guard. Keep CM's established line-catalog fallback behavior unchanged.

Extend the existing geometry coverage enum with `partial` for a current retained route set where some routes lack usable shapes or a known bad variant was discarded, and include covered/retained route counts and the known variant limitation in its message. A small optional internal `GeometryPartial` boolean distinguishes newly parsed usable partial geometry from retained fallback geometry: new partial data keeps its current geometry timestamp and sets the flag; fallback clears the flag, preserves the prior timestamp and sets `GeometryError`. Old caches default the flag to false, preserving their existing error → stale behavior. Available means every retained route has at least one usable variant, not every physical track is known. Preserve stale precedence and report unavailable when none exist. Missing individual variants must not fail all otherwise valid geometry; validate the affected shape and surface partial coverage, while optional geometry resource/admission failures may discard the geometry component as a whole. Archive integrity, archive resource limits and source-security failures remain fatal for that refresh. Do not invent stop-to-stop fallback lines.

Reuse paginated `/api/v1/route-shapes`, route filtering and its existing immutable state revisions. Preserve source attribution. Add train and ferry layers/controls to the current map alongside Metro/bus: “Linhas de comboio” for CP/Fertagus, “Percursos fluviais” for TTSL. All switches start enabled; geometry is fetched and drawn only for selected operators. Initial selection stays Metro alone. Identify layer mode from provider metadata, not the current “Metro else bus” fallback. Keep the selected-route highlight above network lines and below stop/vehicle symbols. Static overlays stay visible when a selected provider has no live reports or has a live-source error.

UI toggles use only the local generated API client, never upstream provider requests. Preserve static caching and independent loading/error/stale/partial messages. No routing engine, map editor, geometry database extension, national-network import or generic layer registry.
