# Public CP arrivals and readable transport details

Status: accepted after independent plan and final reviews; main confirms the plan meets the requested scope. Planning checkpoint only. Main owns implementation, tests and fixes; real `quasar-alpha` at `xhigh` reviews independently. User chose station arrival indicators with richer train/station popups and requested readable names for every operator.

## Outcome

Use verified public TML CP TripUpdates to show upcoming arrivals at existing CP station coordinates and enrich existing train/station detail panels. Show route, station and destination names consistently for **all operators** in search, map interaction, detail panels, arrivals, planned-trip lists and fleet station/route fields. Human labels never replace original IDs in joins, API filters, search identity or storage.

The new prediction integration is CP only; other operators retain their admitted sources and benefit from the name/popup presentation fixes. No synthetic train markers, position interpolation, direct CP credentials, Mover API, national GTFS expansion, new history tables, snapshot fields, infrastructure or general provider framework. Baseline Metro-only selection, selected-mode overlays, plates, stopped state, popup dismissal and current/last-known metrics remain.

[Evidence and source-to-feature mapping](research/CP-PUBLIC-PREDICTIONS.md) includes actual duplicate entities, missing service dates/sequences, source age and the unavailable public CP crosswalk. Do not assume HTTP success establishes current prediction coverage.

## Source normalization

Add one concrete CP prediction collector using the existing Fetcher/client, budget transport and response bounds. Fetch `/realtime/eta/gtfs`; do not fetch simplified ETA or the 10 MB network list in the production loop. Run a separate non-overlapping five-second collector loop with a five-second request deadline, so this source cannot delay position ingestion. First fetch at startup, then wait a full interval after each completed attempt; no catch-up bursts or eager retries. Cancellation and cooldown follow existing transport policy.

Normalize against one captured immutable CP static revision. Admit only a valid GTFS-RT 2.0 `FULL_DATASET` message. Reject `DIFFERENTIAL`, deleted-entity replacement semantics and malformed headers as unsupported; never interpret them as a complete empty/current dataset. Admit only exact `[active-plan][N18KL]raw-trip` references found in that revision, with known retained local stations. Preserve published names and source update times. Do not obtain service dates from trip-ID suffixes, provider publication headers, collection time or a bare train number.

1. Map a supplied sequence to the unique matching retained GTFS stop visit in the exact trip. Where Hub IDs are remapped, build a **batch-local** one-to-one crosswalk from these verified matches. Reject conflicting forward or reverse mappings; do not persist or carry mappings across plans. For updates without sequences, use that verified crosswalk only if the exact trip has one visit to the mapped stop. Unknown/repeated stops remain unavailable. Older rows may establish static identifier relationships, but may not supply current operational predictions.
2. Accept scheduled trip/stop relationships only. Missing relationships use GTFS's scheduled default; unsupported/cancelled/skipped/no-data/replacement/unscheduled rows do not become ordinary positive arrival predictions. A conflicting cancellation/skip for the same instance must suppress the positive row, with explicit availability rather than fake zero delay. Do not propagate a delay to unreported stops.
3. Preserve separate `source_updated_at`, publication and collection clocks. Current predictions require a valid original timestamp no more than 90 seconds old and no more than 30 seconds in the future. A 304, restart, cache restore or identical payload never renews source age. HTTP 204/empty valid FULL_DATASET clears current predictions; failed/malformed responses may retain the prior snapshot only until its original age expires. Disappearance does not reuse GPS's one-hour retention policy.
4. Explicit `start_date` takes precedence and must validate against plan/calendar and all supplied descriptor fields. For date-less scheduled trips, resolve an instance only when exactly one active calendar occurrence is compatible with the source timestamp and upcoming event window. Limit date-less signed deviations to ±6 hours; larger deviations require an explicit date. Enumerate the existing maximum GTFS service hours plus that deviation bound around the source date, including calendar exceptions and GTFS's existing Lisbon midnight/DST conversion. Require at least one mapped upcoming event and a single consistent candidate day for the entity's mapped informative events; reject zero/multiple candidates, contradictions and service overlap. Keep the basis (`published` or `matched_schedule`) explicit. An absolute event with no unique service instance may be displayed as an unjoined source prediction at a verified station, with service date/planned time unavailable; do not merge it with a dated planned journey or enrich a vehicle from it.
5. Absolute event times take precedence within a single valid update; delay-only events require that unique dated scheduled instance before calculating scheduled time plus published signed delay. Accept only arrivals from now through two hours ahead. Missing delay stays unknown; zero and negative values retain meaning. Label the deviation as **Desvio previsto**, never measured punctuality. Do not derive a delay by subtracting an uncertain timetable or compute missing events.
6. Duplicate IDs are real. Group candidates by exact plan, trip instance and stop visit, retaining source metadata. Choose newest original update timestamp; identical duplicates collapse; equal-time conflicts fail closed for that visit. A fresher valid delay-only row may supersede an older absolute row only after independent instance/stop validation. Array order, physical vehicle ID and suffix guesses never decide identity. Invalid/unjoinable newer rows do not silently renew an older accepted prediction. Record rejected/ambiguous coverage without exposing raw upstream errors.

Bound decoded input to existing 16 MiB and normalized content to **1,024 rows, 256 services and 256 KiB serialized**, with bounded strings. Overflow rejects the entire new snapshot with explicit unavailable/partial status; never claim a silently truncated map is complete. All normalized rows, source/coverage state and names attach immutably to `State`; 64 retained versions share immutable data where unchanged. A batch built against a replaced static pointer is discarded/retried on the next scheduled fetch. Plan changes invalidate predictions and mapping before a new publication. No prediction storage writes or restart replay.

Existing static data does not retain frequency eligibility or full national journey duration. During the existing CP GTFS parse, record only a conservative plan-level frequency-presence flag and each retained trip's full first/last scheduled seconds, before geographical filtering. Do not retain national stop-time rows. Date-less admission requires verified absence of frequency services, a full journey shorter than 24 hours and no next/previous instance overlap under the ±6-hour bound. If a future plan contains frequencies, block **all scheduled-instance joins for that plan, including explicit-date rows**: `start_date` alone cannot identify a frequency instance. Do not build start-time/frequency expansion. Absolute events may still remain visibly unjoined at exactly verified stations. Old static caches mark these facts unknown and apply the same conservative gate until refreshed. The changed CP metadata format invalidates only legacy CP static cache eligibility, prompting one normal budgeted re-fetch/parse rather than waiting for a six-hour cache expiry or repeatedly fetching. All added static cache bytes count against existing storage guards; no SQL/schema migration is needed.

The extra loop initiates at most 12 requests per rolling minute (one immediately after startup, no overlap). Permitted same-origin redirects can increase this to 36 actual attempts; every attempt passes transport enforcement. Existing shared ceiling stays **900/minute** and TML **120/minute**. Admission must count a complete startup/static-refresh burst, positions, prediction reads and permitted redirects; if capacity is exhausted skip refresh rather than raise limits. Honor existing 429/503 Retry-After/backoff and sanitization. Five seconds is an application polling target, not a claimed published TML quota.

## API and names

Extend the single `api/openapi.yaml` first, generate Go interfaces/types with oapi-codegen/v2 and the TypeScript client with oazapfts. Add one paginated read endpoint `/api/v1/cp/predictions`, using existing `read:transit` authorization, public UI access, incoming limits, expensive-read guards and pinned revisions. No new credential or proxy bypass. Confirm actual scope naming in existing middleware before implementation.

Return normalized stop-call rows with qualified stop/route/trip IDs, human stop/route/destination names, optional passenger service number, nullable service date/date basis, stop sequence, scheduled/expected times, signed published deviation, original/collection clocks, `valid_until` and source attribution. Page metadata remains the existing shape; include a small typed availability/coverage object so empty verified data, loading/uninitialized, stale, partial and failure are distinguishable. Filtering is limited to existing selected operators (CP), optional stop/trip, time window and pagination/revision; validate all bounds. Do not return the multi-operator raw feed or full national calls. Compute the eligible set once against the captured state's time, using identical filters/window on every page. Pinned data/metadata never change through per-request row filtering. If the earliest source-validity deadline of that pinned eligible set passes, reject the entire pinned read with **HTTP 410 `prediction_revision_expired`**; the UI discards incomplete pages and retries a fresh revision at most once. The deadline is the earliest included source update time plus 90 seconds; no deadline is renewed by a newer State carrying unchanged predictions. Each row also carries its own source deadline, and the UI hides it after either that deadline or its predicted arrival passes. An expired prediction cannot become current through an old revision. A source-expired latest set returns stale/unavailable coverage and no current rows on the initial unpinned read.

Station panels use this cached query alongside existing `/arrivals` planned data; train panels filter the same cached dataset. No backend per-visitor upstream calls and no generic arrival-engine rewrite. Current `Arrival.trip_id` is a generated dated instance ID, not the source-qualified GTFS trip ID. Add optional nullable typed **`plan_id`, `source_trip_id`, `service_date`, `stop_sequence`** association fields to `Arrival` in OpenAPI, and fill them directly from `scheduleQuery`'s captured StaticData, original `ScheduledTrip.ID`, known service day and original `StopTime.Sequence` (zero is valid). Preserve current opaque `id`/`trip_id` unchanged; never parse their suffixes. Prediction rows expose the same source-qualified identity convention. Include a nullable named `route_name` where needed for all-operator arrival labels, sourced by exact route association rather than ID splitting.

Pin station prediction and planned-arrival reads to the **same State revision**, preserving filters/window during paging. Merge/deduplicate only when every typed key agrees: `(operator_id, plan_id, source_trip_id, service_date, stop_id, stop_sequence)`, and the prediction's scheduled time agrees with that exact planned visit. Missing fields, undated predictions, different plans/revisions or contradictory times remain separate; do not infer a bridge from clocks or opaque IDs. Use predicted time for the matched row's display/order. A changed selection/expired revision discards the combined result and retries the bounded shared-revision read once; planned schedules remain available separately if predictions are unavailable. Keep unchanged Metro scheduling/prediction semantics outside this change, and do not force a typed association onto its direct predictions.

Attach predictions to a vehicle popup only when its existing **explicit observed operating date**, exact active plan/trip and a resolved prediction instance agree. Never use a prediction's service number as a physical vehicle identity. Missing association gives a precise unavailable explanation and retains existing planned origin/destination. Publication of predictions must not renew vehicle observation timestamps or last-known positions.

For all operators, prefer exact-associated stop names, named routes and published headsigns; use full journey endpoints only when available and label them planned. Backend adds named fields only where the current contract lacks them; generated types remain the authority. Replace the current `route_id.split(':')` line label and prominent `paragem <source_id>` copy. Keep valid passenger route numbers and published service labels, but hide database/internal IDs from ordinary headings. Never invent a train number by splitting an unverified trip suffix.

Use one small shared presentation helper where needed, not a naming service or remote catalogue. Trim/normalize whitespace, preserve accents/Unicode and meaningful abbreviations. Use a tiny operator-specific, source-cited alias only for verified display corrections such as Santa Apolónia; aliases never participate in matching. Fall back to `Estação/Paragem/Destino/Linha indisponível` as appropriate. Add accent-insensitive name/alias search to the currently lower-case-only route/stop search; keep existing ID lookup and pagination/identity behavior. Reuse one small normalization function and include display aliases in matching, without changing stored IDs/names. Render untrusted names as escaped React text, never HTML.

## Map and popup behavior

Existing station points receive a small distinct CP arrival indicator, with accessible legend and a next-arrival minute label at useful zoom levels. This represents an upcoming **prediction at a station**, not a train's current location. Use existing station coordinates; display only selected CP stops, with the Paragens visibility control respected. No new overlay control. No station badge when no eligible prediction exists; the panel explains partial/unavailable predictions and still shows planned schedules. Expire badges and countdowns locally even if a query fails. UI receives all bounded pages pinned to one revision before replacing the visible set; no first-page-only coverage claim.

Station panel: readable station/operator title; upcoming service label, named line/destination, predicted arrival, planned time where uniquely matched, signed deviation and original update age/source; planned-only rows visibly labelled. Train panel: passenger label, planned full origin → destination, reported/stopped/last-known state, named reported station and eligible predicted upcoming calls/deviation, with precise missing-field copy. Missing platform/model remains unavailable; no new inferred fleet information. Future call order is stop sequence for a resolved trip; station board order is expected arrival, with stable tie-breaks.

Keep close button, outside click, Escape and focus behavior. Add loading feedback for initial/background prediction reads and separate source errors from GPS provider status. An unavailable prediction feed must not gray out CP's valid positions or suppress its planned schedules. Poll cached UI queries only while CP/live views need them; cancel obsolete stop/trip requests, and prevent late results from the prior selection appearing in a new panel. Desktop and mobile names may wrap; do not hide meaningful destinations behind technical tokens.
