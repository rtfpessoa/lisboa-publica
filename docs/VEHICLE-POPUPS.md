# Directions and independent stop times

Station popups show a matrix of lines and directions, with the selected direction beside “Próximas chegadas e partidas”. Direction buttons omit result counts and repeated “Cobertura por confirmar” labels. The selected timetable labels rows and totals as results: independent forecasts need not identify distinct operated journeys. The default destination is not repeated in every row; a different short-service destination is shown on that visit. Arrival and departure have independent evidence and missing values.

[Station presentation](../frontend/src/stationIdentity.ts) groups a published parent station and its verified child stops into one map/search/popup entry containing all station directions. A selected child opens the verified parent; the original source stop and visit identities remain unchanged. Missing parents, cycles and cross-operator parent references retain the original stop. Names or proximity alone never merge stops. Nearby navigation keeps its initial station/stop anchor within 50 metres, reconciles current selected operators and catalogue data, and uses the same eligible list for buttons and target selection. Disabling an operator excludes its stops; hiding its route-geometry layer is independent.

Vehicle popups show the complete safely associated journey, including visits outside the map area and repeated visits to the same stop. The initial page contains the next uniquely identified visit; users can navigate to the beginning and subsequent pages. Existing map paths, nearby-stop navigation, verified vehicle links and published specifications remain available. CM vehicles without an identified journey retain the separate verified published-pattern path or next-stop fallback.

Vehicle positions remain on the map for ten minutes from their original source clock, for every operator. At five minutes without a newer position, the marker gains a small amber warning and the popup footer explains the update gap. Popups show “Última atualização do veículo” using the original position clock. “Recebido pela aplicação” uses that record's collection clock and appears only when its formatted Lisbon time or age differs from the update line; second-level differences that produce identical visible text do not add a duplicate row. Both API clocks remain unchanged. Repeated reports retain those clocks; the local one-second display timer continues during request failures. Estimated-position provenance remains available in source information; the common Metro estimate classification does not add a per-vehicle warning or pill. After expiry, an already open detail retains its attributes and journey consultation with “Sinal expirado”; cached evidence is not presented as current progress. Stable verified attributes persist independently of position/history expiry.

## Cached reads and identity

The additive station board and vehicle journey operations are defined in [OpenAPI](../api/openapi.yaml). Generated Go and TypeScript contracts must be regenerated from that file. Boards default to a two-hour interval and retain all known direction groups independently of the displayed page. Vehicles default to 100 visits per page, up to the existing 500-row limit. No browser read fetches an upstream source.

Board revisions freeze the network and, for requested-stop sources, a publication held by the existing bounded arrival lease. Expiry, eviction or restart requires a fresh board revision. Journey revisions freeze the network/observation, read instant and committed stop-event generation. An omitted journey offset focuses the next visit; an explicit offset selects that page. Visible popups honor `Retry-After`.

For operators other than Metro, [station refresh](../frontend/src/useStationBoard.ts) assembles the board and its selected result page before replacing the visible frame. Each next refresh starts five seconds after the previous attempt settles. Delayed or failed requests retain the previous complete frame and its original evidence clocks; an update failure is shown separately. Revision expiry retries once with a fresh board while retaining the selected direction/page. If the selected page no longer exists, the controller reads the nearest valid page under the same revision before publishing it, keeping the direction and applying normal reading-anchor recovery. A removed direction remains explicitly unavailable until the user chooses another; a late response from an older selection cannot replace the new selection. This is frontend response coherence, not one transaction spanning all dashboard reads.

[Reading preservation](../frontend/src/useStationReading.ts) keeps surviving visible content at its position in the popup, including inserted/reordered results and local expiry changing row heights. Keyboard focus stays on a surviving control; a removed row falls back to a following surviving row, then a preceding row, or the remaining scroll bounds. Explicit direction/page choices may move to the newly selected content. Polling does not refocus the popup or scroll to its beginning. Forecasts still expire every second while offline and never become actual occurrences.

A vehicle journey requires a unique trip, matching operator/route/plan and explicit operating date. Frequency-based schedules without a uniquely identified instance and duplicate or unordered visits fail closed. Repeated stops without a published progress sequence do not produce a guessed next visit. The approximate Metro Hub trip assignment does not qualify; an independently identified direct Metro destination can still be shown.

Metro can instead expose an ordered published route with `association=published_route`, separate from a timed journey. The current plan and route must match. A unique approximate Hub trip supplies the line/direction path; a conflicting fresh direct destination rejects it. Without a trip reference, an exact fresh direct train destination can select the route only when all matching static candidates have identical stop IDs and visit sequences. Missing plan, route, destination/orientation, conflicting paths, duplicate trip IDs or unordered visits leave the route unresolved. This fallback requires no operating date and admits no timetable, predictions or historical actual times. `journey_id` remains null.

The compatibility published-route projection labels this as the line's published route with an estimated association to the train, displays ordered stops without arrival/departure columns, and retains verified stop navigation. Progress is at most estimated and requires a fresh published stop/status and one uniquely matching visit; stale or repeated-stop observations leave it unknown. The routine unresolved Metro association warning is omitted, as is the separate unidentified-service notice; request errors, coverage, expiry and other warnings remain visible. Other operators retain the unresolved journey warning. Route pagination uses the existing frozen journey revision and read limits, with no upstream requests or stop-event reads.

Journey stop rows carry the supplying static plan and update clock when a navigable catalog stop is available. The shared row renderer forwards both to the existing navigation revalidation; the current catalog must still match before the station opens. Sources without a plan identity leave it absent.

Metro variants share a direction only when the entire shorter parent-stop sequence occurs in the same order in the longer route. Ordinary directions remain scoped to their published route. Journey destination and direction are separate concepts.

## Sources, clocks and gaps

GTFS parsing retains full visits alongside local map visits, sharing the sequence when every visit is local, including independent missing arrival/departure clocks. Service times above 24:00 follow the operating day in Europe/Lisbon, including daylight-saving transitions. The existing four CM archives also provide merged schedules, with explicit line mapping and plan/agency-qualified trips and services. Old static caches refresh through the normal collector. Stop identities share catalog strings, cached schedules restore one trip at a time, and station-to-trip lookups retain at most 32 selected stops within a 4 MiB index budget per network revision. Route/direction catalogs and CM source metadata are shared across trips. Exact GTFS stop-to-line membership narrows station reads. Road-operator local visits use lossless compressed variable-length deltas for stop identity, sequence and independent clocks; they decode only for reads. Complete visits are never removed to meet these budgets.

The existing shared TML ETA request is decoded once for CP, bounded operator publications and requested-stop arrivals. Operator capacity exhaustion marks that operator partial without invalidating other operators. The native CM requested-stop collector and its existing budgets remain active. Predictions without a safe dated instance remain separate station calls and do not inherit vehicle timetables. Collection never resets the original source clock or expiry; source publication time is absent where not supplied.

[Station coverage](../internal/app/popup_station_coverage.go) describes usable evidence in the response: the complete assembled board for direction discovery, and the returned selected page for result reads. A valid direct Metro prediction is not hidden by an unrelated stale TML publication. Valid planned schedules remain partial coverage when forecasts are unavailable; stale static networks retain their warning. Native published scheduled evidence can remain available without a GTFS timetable. The coverage source clock is the latest original update among contributing usable predictions, or absent when none supplies it. This does not mean every source has that freshness. The selected page has one coverage notice, and the unsupported actual-history limitation is appended at most once. Retained forecasts losing validity locally degrade the notice as well as their displayed times.

No current adapter is certified to collect actual stop arrival/departure occurrences. Historical gaps show “Sem registo real”. An elapsed forecast, a GPS position or STOPPED_AT status never creates a real event. Arrival does not establish departure.

The internal stop-event boundary can accept explicit occurrences from future validated adapters. Events become visible only after durable commit; versions are deduplicated and corrections require explicit higher source revisions. Contradictory occurrences remain unavailable. The history budget, retention and collection pause apply to these records. See [history](data/history.md) and [associations](data/associations.md).

## Verification scope

Go tests cover all eight operator identities, safe joins, repeated visits, missing clocks, service dates, cache serialization and durable PostgreSQL event versions. [Coverage regressions](../internal/app/popup_station_coverage_test.go) exercise contributing source clocks, planned fallback, expiry and duplicate notices. [Refresh fixtures](../frontend/tests/station-refresh.spec.ts) exercise changing revisions, delayed calls, offline expiry, removed-page recovery, reading/focus preservation and obsolete responses at desktop/mobile widths. [Navigation fixtures](../frontend/tests/stop-navigation.spec.ts) cover station hierarchy and operator changes alongside nearby selection. Synthetic fixtures validate behavior, not guaranteed production source coverage.

Dated acceptance evidence, including the enforced Linux memory workload, is in [vehicle popup validation](research/vehicles-ui-validation/VALIDATION.md).

Vehicle details show the backend-owned signal separately from the published physical stop status: receiving updates, no current signal, or unconfirmed signal. Missing normalized membership and old observations explain no-signal states; source failure/unverified collection explains uncertainty. A `not_reporting` signal immediately adds the marker warning without waiting five minutes. The original five-minute age warning and ten-minute display expiry remain independent. Pending state/clock persistence is noted in the source footer. See [reporting state](data/README.md#backend-owned-reporting-state).

## Metro live popups

The current Metro UI uses [a shared dynamic SSE/snapshot frame](metro-live-popups.md), including all supported
identified references in the selected line/direction, independent missing ETA rows and separate old/ambiguous
records. Vehicle selection pins an inferred journey, shows ordered previous/current/remaining visits, original
inferred arrival evidence and separate official/experimental own forecasts. Visits behind the train's marker show
occurrence or retained last-official-estimate times instead of countdowns, and forecast/context lists follow the
published stop order. The Metro operator row reports Hub model-position availability
(`model_position_state`, `last_model_position_at`) without changing operator status. Countdown expiry does not
create events.
Departure remains unavailable without calibrated movement provenance. Follow starts with support, manual pan/zoom
pauses it and explicit resume retains the selected run. Next-station navigation scrolls the list only.
See [browser delivery](../frontend/src/useMetroLive.tsx), [Metro popup UI](../frontend/src/MetroPopups.tsx)
and [browser checks](../frontend/tests/metro-live.spec.ts). Legacy board/journey API operations remain available
for compatibility and other operators; their route-only limitation does not describe the new Metro frame.
