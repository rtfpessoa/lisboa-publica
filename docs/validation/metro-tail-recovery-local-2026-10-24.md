# Metro tail recovery local evidence, 2026-10-24

This is a local rehearsal, not a deployment or a complete production-volume test. Three read-only copied, checksum-verified production generations were placed in a synthetic manifest: the Metro checkpoint, its same-hour detail, and the affected daily aggregate. The verified checkpoint contains 99 receipts; the detail contains one later receipt, with no issued forecasts and 41 evaluated proxy outcomes matching pending cases. The daily aggregate equals the checkpoint for the affected day. The raw-only repair retains the tail and omits those outcomes and tail coverage from aggregates; it does not establish physical arrival times.

The Go 1.26.10 Linux/arm64 repair binary ran with a 768 MiB cgroup limit, `GOMEMLIMIT=384MiB` and `GOMAXPROCS=2`. It reported `repaired`, then `already_applied`; cgroup peak was 405,905,408 bytes and all OOM counters were zero. Separate copies of the same synthetic inputs produced identical repaired state and manifest hashes. The full archive has additional references and requires a separate stopped-volume rehearsal with its own manifest hash and capacity checks.

On another disposable repaired copy, the actual earlier server image at revision `175596d831808c8f4d8e68431add2ccbab857159` started against an isolated PostgreSQL container, served health, and reported Metro as paused. Its startup reconciliation removed the original, unreferenced checkpoint generation while leaving the repaired manifest unchanged. Strict old checkpoint decoding therefore does not prevent old server startup or protect all source evidence. Keep a separately verified backup and externally prevent an incompatible executable from opening the repaired volume.
