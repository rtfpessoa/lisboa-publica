# CP realtime coverage and missing service details

Checked 26 September 2026, approximately 18:33–18:44 UTC. This is an investigation and a correction plan, not a new CP integration. No backend, OpenAPI contract, upstream polling or production settings were changed. The separate popup changes are local UI work.

## Findings

The CP adapter consumes TML's normalized positions only. It does not consume CP's travel API, CP TripUpdates or TML arrival predictions. Those sources expose different information. Current empty CP markers can reflect a real upstream coverage gap; retaining previous positions does not create new observations. Missing origin, destination and delay fields also have a contract/UI cause: the current Vehicle schema and detail view do not expose them.

Repository references: [provider configuration](../../internal/app/data.go#L27), [position decoder](../../internal/app/ingest.go#L83), [CP normalization](../../internal/app/ingest.go#L435), [metadata enrichment](../../internal/app/ingest.go#L501), [source-of-truth API](../../api/openapi.yaml), [detail UI](../../frontend/src/App.tsx).

At the first capture, TML returned 771 position rows and **zero CP rows**. Our application returned 21 CP rows, all last-known and none current. A later official response contained 15 CP rows, and a paired check of the legacy and current position URLs returned the same generated dataset: 782 rows, including six CP rows and none in a box with absolute latitude/longitude differences below 0.008° from 38.7677574, -9.0990944 (not a distance radius or platform boundary). Thus an endpoint rename alone is not a demonstrated fix. The six-row paired sample is not a national fleet count or a guaranteed operating count.

Oriente's official coordinates, approximately 38.76776, -9.09909, are within our existing Lisbon bounds. There were no upstream CP rows near Oriente to reject during these captures. This rules out local geographic filtering as the explanation for that specific missing-marker sample; it does not prove every historical gap has the same cause.

CP's own website provides richer service data. Its ordinary station detail page fetched 32 Oriente timetable records, eight with non-null delays. Train 4432 had scheduled arrival 20:12, ETA 20:14, delay `2`; the public page displayed two minutes. Train 574's detail returned `AT_ORIGIN`, last station `94-31039`, platform 7 and delay `72`, displayed as 72 minutes. Crucially, its **top-level train latitude and longitude were null**; coordinates inside its stop list were station coordinates. These are not evidence of an onboard GPS position.

Earlier comparison-site observations showed a richer CP adapter and markers near Oriente, but did not identify its exact provider URL or prove how its coordinates were produced. Those observations are comparison evidence only. After the user's explicit clarification, no further Mover Lisboa API calls were made. No Mover API is configured or proposed as an application dependency.

The [official CP collector](https://github.com/tmlmobilidade/go/blob/prd/modules/tracker/apps/pt-tml-cp-api-fetch/src/index.ts) polls partner VehiclePositions and uses each vehicle's timestamp; its [parser](https://github.com/tmlmobilidade/go/blob/prd/modules/tracker/packages/parsers/src/pt/tml/cp/v1.ts) copies upstream coordinates. That establishes what TML ingests, not why CP or TML omitted a particular train. It also does not establish the exact source used by another website.

Identifier caution: CP's travel API uses `94-31039`; the inspected GTFS uses `94_31039`; TML ETA used stop ID `253542` for Oriente. Service codes also vary (`IC` versus numeric `2`). Require an explicit, validated crosswalk within the selected plan; do not join by station display name or blindly replace punctuation. A train number is a service identity, not a confirmed physical fleet vehicle. Include the operating date where service identity requires it.

## Minimal correction plan

1. Preserve the current source, truthful zero/unknown counts, one-hour original-time retention and five-minute inactive state. Record bounded CP-specific source coverage counters so missing upstream rows can be distinguished from rejected rows. No fabricated markers or observation timestamps.
2. First expose **scheduled** origin/destination using an exact current-plan trip match. Complete endpoints are not currently retained: the parser discards non-Lisbon stops and their stop times. Retain only bounded original first/last service endpoint IDs and names during GTFS parsing, before region filtering; do not broaden the retained network or infer whole-journey endpoints from retained `Times`. Legacy caches without verified complete endpoints show unavailable until a normal static refresh supplies them. Add only the necessary optional fields to `api/openapi.yaml`; regenerate Go interfaces and the TypeScript client. Show missing or unverified joins as unavailable.
3. Confirm application access to CP partner and/or travel APIs, their reuse terms and numerical rate limits before adding a collector. Prefer bulk positions and TripUpdates if available; use the travel API for details that those feeds lack. Evaluate coverage directly at Oriente, including trains at origin and platforms, against original observation timestamps. Never adopt website credentials as our server credentials.
4. Fetch shared server-side data, normalize only verified fields, cache results and preserve separate service/vehicle/position provenance. CP JSON delay is minutes; GTFS-RT delay is seconds. Null means unknown, not zero. Resolve Lisbon local service dates, midnight and DST explicitly. Do not treat a future arrival prediction as a position observation or proof of completed travel.
5. Fit new requests, OAuth, redirects and retries within the existing 900-attempt rolling minute ceiling and below the user's 1,000 limit, plus any stricter verified provider quota. The current 1-second TML collector cadence and website cache settings are not permission for our polling rate. Coalesce demand, use bounded active-service/station caching, back off on 429/Retry-After and outage, and cap concurrency; avoid per-user polling fan-out.
6. Test exact and mismatched joins, minute/second conversion, absent coordinates, omitted trains, upstream failure, stale and repeated clocks, day-boundary identities and rates. Browser acceptance must show service details where verified and retain clear reported/estimated/last-known distinctions. New source integration requires its own independent plan and final reviews.

If direct access is unavailable, retain the existing reported map and show richer scheduled service details; evaluate TML ETA separately as experimental predictions. A station-based estimate is a separate product decision and must never enter reported position counts, sampled speed/distance or physical fleet metadata.

## Evidence and limits

[Sanitized official observations](cp-realtime-coverage/official-evidence.json) record endpoint paths, response counts and selected public data without any credential values. Checks included repository normalization/contract/UI review, ordinary CP site navigation, anonymous access verification, the official TML collector/client/parser source, existing GTFS files, public position snapshots, a paired legacy/current-path check and one TML ETA snapshot. No partner feed was probed with credentials, no brute-force/path enumeration or load test was run, and no production changes were made. A short capture cannot establish uptime, long-term coverage, exact comparison-site upstreams or the cause of CP's upstream omissions.
